HexWin, for Linux

Hex is a hold-to-talk dictation app for macOS, and HexWin is its Windows answer. HexLinux is the same idea for the Linux desktop — hold a key, speak, release, the text lands at your cursor, and nothing leaves the machine.

It is HexWin’s sibling rather than a port: the same engine, the same architecture and the same diagnostic modes, written again for the platform — C# on .NET 10, the kernel’s input devices, PulseAudio or PipeWire, and the clipboard and keystroke tools of X11 and Wayland. Underneath, as in the other two, is NVIDIA Parakeet TDT v3.

If you landed here looking for an offline dictation tool for Linux: this is free, open source under Apache 2.0, runs on CPU, and asks for no account.

It answers before you finish thinking

The time the engine takes to transcribe, measured under Linux — WSL2, Ubuntu 24.04 — on a Core Ultra 7 255H, the processor of HexWin’s own figures, on CPU with four threads. No graphics card involved.

Speech lengthTranscription time
5 s0.215 s
40 s1.616 s

The loaded model holds 0.8 to 1.1 GB of memory, which is why it is released after five idle minutes and loaded again as you press the key, while you speak. Figures on a native Linux install are still to be recorded.

Why it is fast: Parakeet, not Whisper

HexWin tried Whisper first, and dropped it after measurement. Whisper is an autoregressive encoder-decoder, so it pays a fixed cost on every transcription however short the audio is; on a single sentence, that cost is paid in full.

Parakeet TDT v3 is a transducer and has no such bottleneck. On Windows, HexWin measured the same five-second clip at 2.29 s with Whisper on GPU and 0.19 s with Parakeet on CPU.

It is the engine Hex uses on macOS too, and it recognises the spoken language on its own among 25 European languages — the language you dictate in is never a setting to get wrong.

Two ways to dictate

Hold a key

Seeing a key held down, whatever window has the focus, means reading the keyboards under /dev/input, which an ordinary user may not do. The archive carries an installer for a udev rule that grants it to the user of the active session. That permission reaches every program you run, not only HexLinux: the README says plainly what it grants before you decide.

Press a shortcut, with no permission at all

Bind hexlinux --toggle to a shortcut of your desktop — GNOME, KDE Plasma, Sway, Hyprland all have a place for one. Press it to start, press it again to finish. The desktop handles the key, and HexLinux reads no keyboard.

A long dictation does not have to wait for the end: with segmentation on, each pause in your speech — 700 ms by default, up to 5 s — closes a piece, transcribed and inserted while you keep talking.

Nothing leaves your machine

  • No cloud, no account, no API key. Once the model is downloaded, HexLinux needs no network connection at all.
  • Your audio never touches the disk. The recording lives in memory and is gone the moment the transcription ends.
  • The keyboard is watched, not taken. HexLinux never grabs a keyboard, so every key still reaches your desktop, and it looks at the keys of its shortcut and nothing else. It stores no keystrokes. The code is short and meant to be read: src/HexLinux/Input.
  • Your words stay where you put them. The log keeps durations, sound levels and character counts, never the text. The text is handed to the clipboard and keystroke tools on their standard input, never on a command line that every user of the machine could read.

Three commands to start

Download hexlinux-linux-x64.tar.gz from the latest release, extract it, then in that folder:

./get-model.sh      # about 490 MB, once, checked before it is extracted
./hexlinux --doctor # what HexLinux can see of your session
./hexlinux

Nothing to install for HexLinux itself — not even .NET, which is bundled inside the executable. The clipboard and keystroke tools come from your distribution, and --doctor names the ones your session is missing. ./hexlinux --autostart on starts it with your session.

You can tell it is listening

A short tone marks the start of a recording, a lower one its end. On desktops that show tray icons — KDE Plasma, Xfce, Cinnamon, the bars of wlroots compositors, and GNOME with the AppIndicator extension, which Ubuntu enables — an icon carries HexWin’s colours:

  • loading the model
  • ready
  • recording
  • transcribing
  • model not found

Its menu dictates, opens the settings file and the log folder, switches the tones and the start at login, and quits. Failures that need you — model missing, microphone missing, text that could not be inserted, a locked screen — arrive as desktop notifications, which never carry what you dictated. Where there is no tray, HexLinux runs all the same, and says so in its log.

What to expect, stated up front

  • The keys of the shortcut still reach the desktop. Linux has no way to hold a key back short of grabbing the whole keyboard, which would put HexLinux on the path of everything you type. The default, right Ctrl alone, does nothing on its own.
  • GNOME and KDE on Wayland accept keys from no ordinary program. Pasting there needs the virtual keyboard rule the installer offers, and the simulated-typing mode is not possible at all. X11 sessions and wlroots compositors are simpler.
  • Clipboard history keeps the dictation. In the default paste mode, clipboard managers record the text; unlike HexWin on Windows, HexLinux has no way to keep it out of them. The typing mode leaves the clipboard alone, where the session allows it.
  • A locked screen is seen through logind, and only lockers that tell logind are: GNOME’s and KDE’s do, swaylock and hyprlock do not.
  • No circle on the screen, unlike HexWin: a Wayland window cannot place itself, and GNOME offers no way around it. The tray and the tones carry the signal.
  • The interface is in English. The dictation itself is in whatever language you speak.

How it is built

Two layers, kept apart on purpose, as in HexWin. The shells — keyboard reader, microphone, engine, clipboard and keystroke tools, tray — wire up the system and decide nothing. Every decision lives in a pure layer tested without a desktop: chord detection, keyboard auto-repeat, keys released out of order, a key left held on a keyboard that was unplugged, a second dictation started while one is still transcribing, the right tool for each kind of Wayland session.

Build and unit tests run anywhere Linux does. The keyboard, the virtual keyboard, the tray and the screen lock need a real desktop session, and the repository says how each one is checked by hand.
